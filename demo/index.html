How Tarpit decides — fingerprint + 3 pit checks

Versatile, but deliberately tight. Every session gets a fingerprint first, then three checks that look for how rogue agents actually behave — not just a bad password.

1

Sequence

Is the order of requests human-plausible? Hitting /secrets/ before discovery, or skipping OIDC steps, scores badly.

2

Consistency

Does the claimed identity match the behaviour? A “user” with an agent user-agent, machine timing and no browser signals fails consistency — the HF swarm scored 0.

3

Coordination

Is this one login, or a swarm? Same leaked credential, same fingerprint pattern, hundreds of hits in 90 seconds — coordination catches what single-login checks miss.

🪤 Trap briefly

Flagged agents don’t reach real IAM. They’re diverted to decoys — fake IAM, canary tokens, a fake /secrets/prod.env, decoy LDAP and a fake repo — long enough to confirm the fingerprint.

🧭 Trace

Origin, entry point, coordination channel and target are recorded per fingerprint, so you can see where it came from and where it was trying to go.

✕ Remove, don’t just hold

Holding agents bogs the network down. Tarpit terminates the session, revokes tokens, and blocks the fingerprint at the edge — then that fingerprint can be flagged on other networks that opt in.

What “live” would look like for a team

This page is a simulation. A real deployment runs only on systems the owner controls or has hired Tarpit to protect — that’s the model for selling it to big tech.

Safe rollout

  • Run as a gateway in front of ForgeRock IAM (Docker on AWS is the usual fit)
  • Start monitor-only — fingerprint and log, don’t block real users
  • Then enforce: divert → confirm → remove
  • Log minimally: fingerprint + behaviour, not personal data

Guardrails by design

  • No hacking back — trap, trace, remove only
  • Cross-network fingerprint sharing only with opt-in
  • No real credentials in any decoy — canary values only
  • Brief trap time (8s in the HF reference run) so the network doesn’t clog
